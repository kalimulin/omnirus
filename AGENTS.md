# Инструкции для ИИ-агентов

## Расположение бэкенда и сверка с документацией API

При работе с API, интеграцией и логикой функционала обязательно сверяйтесь с актуальной документацией и кодовой базой бэкенда:

- **Папка с бэкендом проекта:** `D:\code\shortcut-php` (используйте для проверки реализации контроллеров, роутов, валидации, DTO и сущностей)
- **Базовый URL:** `https://shortcut-external.fenimore.skroy.ru`
- **Swagger нашего API:** https://shortcut-external.fenimore.skroy.ru/docs
- **Проверка, что бэк жив:** `GET https://shortcut-external.fenimore.skroy.ru/info` → ожидаемый ответ `{"version":"0.1.0"}`

Перед началом работы с API рекомендуется проверить доступность бэкенда через `/info` и сверить контракты (эндпоинты, HTTP-методы, параметры запроса, тело запроса, формат ответа и ошибок) по Swagger (`/docs`) или кодовой базе бэкенда (`D:\code\shortcut-php`).

## Работа с функционалом, методами API и моками

При работе с определённым функционалом:

1. **Добавляйте несуществующие методы** — если для задачи требуются эндпоинты из актуального API, которых ещё нет в клиентском слое (`src/api/`), реализуйте их с актуальной типизацией.
2. **Исправляйте изменившиеся методы** — при расхождении существующих методов, путей, параметров или типов данных со Swagger приводите клиентский код и типы в соответствие с документацией API.
3. **Удаляйте неиспользуемые моки** — убирайте устаревшие или неиспользуемые моки, заглушки и fallback-данные, которые больше не применяются в рабочем коде (не затрагивая нужные моки для unit-тестов).

## Стили и переиспользование компонентов проекта

Всё, что создаётся или изменяется в UI, должно соответствовать общим стилям проекта и использовать существующие компоненты:

1. **Единые стили и дизайн-токены** — используйте CSS-переменные и токены темы из `src/styles/variables.css`, `src/styles/colors.ts` и `src/theme.ts` (цвета, отступы, радиусы, тени, шрифты), не хардкодьте произвольные цвета и стили.
2. **Переиспользование компонентов** — перед созданием нового UI-элемента проверяйте существующие компоненты в `src/components/` (`atoms/`, `molecules/`, `organisms/`, `shortener/`, `layouts/`) и используйте их (например, `StatusBadge`, `DateRangeSelector`, `QrModal`, `EditLinkModal`, `DeactivateLinkModal`, `RedirectModal`, `ProgressModal`, кастомные инпуты/кнопки/иконки и т. д.), не дублируя существующую логику и вёрстку.

## Написание тестов

По умолчанию **НЕ создавайте и НЕ пишите новые тесты** (unit-тесты, интеграционные тесты, e2e и т. д.), если пользователь явно и прямо об этом не попросил:

1. **Не создавайте новые тесты по умолчанию** — решайте задачу изменениями рабочего кода, не добавляя новые файлы тестов (`*.test.ts`, `*.test.tsx`) и новые тестовые сценарии без явного запроса пользователя.
2. **Проверка через существующие средства** — проверяйте корректность через запуск сборки (`npm run build`) и существующий набор тестов (`npm test -- --run`).
3. **Обновление только при необходимости** — если в результате задачи легитимно изменилось поведение, из-за чего падают уже существующие тесты, исправляйте только сломавшиеся утверждения в существующих тестах, не расширяя их новой тестовой логикой.
